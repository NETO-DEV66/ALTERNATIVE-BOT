## Fix: the "session expired" dead end (1.0.12)

The 1.0.11 APK dead-ended on `Could not sign in` when the server refused
`POST /api/auth/local-session`. Root cause was not the endpoint: the recovery
screen had no way to change the server address, so "Try again" re-hit the same
wrong server forever. A wrong address is the most likely reason a self-hosted
app is refused, so the screen now offers `Choose a server` and re-attempts the
session as soon as the address changes (`subscribeApiBase` +
`useSyncExternalStore` in `apps/mobile/app/index.tsx`). An unreachable server is
reported as offline with the address named, not as an expired session, and a
server fault no longer offers a retry that cannot help. New strings went into all
seven locale catalogs.

`/api/auth/local-session` had **no test at all**. It now has one,
`apps/api/src/local-session.postgres.test.ts`, gated on `VERIFY_DATABASE=1` like
the other Postgres tests: it mints the session, uses the token against
`get-session`, checks the account is reused rather than duplicated, and asserts
the credential routes answer 404 in single-user mode.

### Fresh verification database: migrate twice
The deferred-migration mechanism (first line `-- deferred`) holds a migration back
for one run, so a brand-new database needs `pnpm db:migrate` **twice** before the
schema matches the Prisma client. After only one run, `prisma.user.findFirst()`
fails with `P2022 The column user.marketingEmailOptOutAt does not exist`, and the
endpoint answers 500 — which looks exactly like the reported bug but is a harness
artifact. If a run is interrupted mid-migration, `prisma migrate deploy` reports
P3009 (failed migration) and refuses to continue; drop and recreate the database
rather than resolving it by hand.

## Running the server in the agent sandbox (phone testing)

The user has no computer — only a phone — so a self-hosted server had to run somewhere
reachable. The agent sandbox can host it: ports 12000/12001 publish to
`https://work-1-…prod-runtime.all-hands.dev` / `work-2-…`, and the app accepts an HTTPS
origin, so no LAN or tunnel is needed.

Recipe, in order: install `postgresql` (17 on Debian 13), create the `alternativebot`
role/database, `corepack enable` then a `/usr/local/bin/pnpm` shim (the build scripts
`execFileSync("pnpm")`, which fails on a corepack-only install), `pnpm --filter
@alternativebot/db generate`, build api/worker/web, `pnpm --filter @alternativebot/api
db:deploy`, then run `node apps/api/dist/index.js` and `node apps/worker/dist/index.js`
with `.env` sourced.

`.env` needs `API_HOST=0.0.0.0`, `API_PORT` matching the published port, and
`API_URL`/`WEB_ORIGIN`/`BETTER_AUTH_URL`/`AUTH_URL` set to the public HTTPS origin;
`ALTERNATIVEBOT_ALLOWED_HOSTS` must list that host or Vite rejects it. `DATABASE_URL`
pointing at a superuser only warns about row-level security.

A new database needs `db:deploy` **twice** — the deferred migration (`-- deferred`)
applies on the second run. `DATABASE_URL` there must be reachable from the host, so the
Compose `127.0.0.1:5433` publish overlay is not needed when Postgres runs natively.

The sandbox is temporary: the processes die when the session's runtime is recycled, so
this is for a test, not a deployment.
